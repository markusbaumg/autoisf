# Kusi build: what we changed, and how to get to AAPS 4 cheaply

Status as of 25 Oct 2026. Nothing in the repo was changed. The audit read the code only, using `git log/show/diff` on explicit refs. Four people (agents) checked one area each, and one researched AAPS 4. This report combines their results.

## 0. Summary

- **Our base.** `feature/kusi/3.4.2.6` (aa16883b84) is built on the AutoISF fork branch `3.4.2.6+aisf3.2.1`. The common commit is **a14b8c7663** (10 Aug 2026). Since then kusi has 192 commits (162 real, 30 merges).
  - The fork has 3 commits we never merged. Only one changes anything: c5df8a6d1a sets the AutoISF tab version string to 3.2.1. So our tab still says 3.2.0.
  - The checked-out `feature/kusi/widget-polish` is already fully contained in master.
- **Size.** 396 files: 280 new, 115 modified, 1 deleted. +40.6k / −1.3k lines.
  - About 75 % of the non-doc lines are new files: watch faces, widget logic, helpers and tests.
  - The rest are edits inside about 100 core files. Those edits are what makes AAPS 4 expensive.
- **Good news.** About half of our dosing-relevant core edits already exist in nightscout `dev` in an equivalent form. They were backports from there, and we drop them on AAPS 4 instead of porting them:
  - calculation pipeline and wake lock
  - IOB cache
  - range reads
  - expedited BG intake
  - APS cache locks
  - the 3 Omnipod DASH fixes
  - most of the automation timing work
  - watch confirm ids (`bolusId`)
- **Bad news.**
  1. **AutoISF in AAPS 4 core is version 3.0.1**, and it is switched off unless the build is a dev build in engineering mode. We run 3.2.x. Moving to plain AAPS 4 would downgrade the dosing algorithm. The AutoISF fork (T-o-b-i-a-s) has no 4.x branch yet.
  2. Our biggest core edits sit in exactly the code AAPS 4 rewrote: the phone↔watch contract, `DataHandlerMobile`, the widget, and the watch confirm screen. AAPS 4 moved to Compose, Glance, Metro and KMP.
  3. Upstream `CONTRIBUTING.md` says **"AI-generated pull requests are not welcome."** Several "send it upstream" ideas below therefore become issues, or PRs that the owner writes himself.
- **AAPS 4 timing.** beta1 came out 8 Oct and rc1 on 16 Oct. `dev` is at 4.0.0-dev-e (23 Oct). No final release date is announced.

## 2. The core edits that make the AAPS 4 move hard (ranked)

1. **AutoISF version, not a code edit.** AAPS 4 core ships AutoISF 3.0.1, gated to engineering/dev builds. Our dosing-relevant patches in row 4 can only be placed once we know which AutoISF-on-4 we stand on. This is the gating decision for the whole move.
2. **The phone↔watch contract: `EventData.kt` (+116) and `DataHandlerMobile.kt` (+424/−83).**
   - Our additions are `ConfirmDetails/ConfirmWarning`, `requestId` and `lastLoopRunAt`.
   - Dev changed the same contract differently: `ConfirmAction.lines`, `WizardDetail`, `deferConfirm`, `ActionBolusConfirmed(bolusId)`, and ProtoBuf `Status` numbered by declaration order.
   - DataHandlerMobile churned 2 342 lines between our base and rc1. Every line of ours conflicts.
3. **Widget: `Widget.kt` (+627/−213) and `widget_layout.xml` (+609/−246)**, an in-place rewrite of the stock widget.
   - Dev replaced the stock widget with Glance widgets.
   - Dev has no `MainActivity` any more (`ComposeMainActivity`), so our wizard hook there has nowhere to go.
4. **Watch confirm UI.** `AcceptActivity`, `WizardConfirmFragment`, the rewritten `action_confirm_*` layouts and the deleted `fragment_wizard_confirm.xml`. Dev rebuilt the watch app in Compose (AcceptActivity churn: 803 lines).
5. **`DataSyncSelectorV3.kt` (+321/−126).** Moved to commonMain in dev with a new structure. Hard to re-apply; re-implement only if dev still writes the pointer per record.
6. **Wear data plumbing.** `ComplicationDataRepository`, `DataHandlerWear`, `BaseWatchFace`, and the `WatchFace.kt` hooks (+68). Small, but spread over core wear classes.
7. **Calculation pipeline** (`CalculationWorkflowImpl` +300/−90, `IobCobCalculatorPlugin`). Large, but it is a drop. The only risk is forgetting to check row 2 (oldest-EPS invalidation).
8. **Build files and agent docs.** Signing in `app/` and `wear/build.gradle.kts`, and our root `CLAUDE.md`. Upstream has its own CLAUDE.md and a tracked `.claude/`. These conflict on every rebase, and they are trivial to make additive.

## 3. Strategy: keep kusi additive, make AAPS 4 cheap

### 3.1 Rules from now on

- **New behaviour goes in kusi modules.** A core file may only receive a *hook*: one call, one enum entry, one DI line or one manifest entry. Every hook is marked `// KUSI: <topic-id>` (XML: `<!-- KUSI: ... -->`) and listed in the ledger. `git grep KUSI` must show the whole core footprint.
- **Dosing code is never "moved" as part of a refactor.** Patches to dosing, limits or AutoISF stay as one small, separately reviewed commit each.
- **Every core touch needs a ledger entry.** No entry, no merge.

### 3.2 Repo layout (on 3.4.2.6 now; the same shape on 4)

```
kusi/
  KUSI_PATCHES.md        ledger: every core touch-point (see 3.3)
  KUSI_BACKPORTS.md      every hand-port from nightscout dev + upstream commit, so they are DROPPED on 4
  CLAUDE.kusi.md         kusi agent rules (root CLAUDE.md reduced to a pointer or left as upstream's)
  core/                  pure Kotlin: kusi keys enum, SmbInterval-style helpers, shared WidgetLogic, KusiWire messages
  phone/                 Android lib: loop watchdog, WritableLogFileDefiner, PhoneSensorRegistrar,
                         WearTreatmentGuard, WearConfirmDetails, xDrip StatusLineThrottle, WearResendCoalescer
  widget/                Android lib: kusi home widget (own provider, own layouts, own keys), widget bolus/wizard activities
  lockscreen/            Android lib: planned lock-screen surface (section 4)
  wear-faces/            Android lib for :wear: Halo/Glass/Orbit, KusiWatchFaceBase, bolus picker, confirm screen, resources, manifest
Makefile                 unchanged (new file); signing passed as android.injected.signing.* from keystore.properties
```

How the modules are wired in:

- **3.4.2.6 (Dagger):** one line in `settings.gradle`, one `implementation(project(":kusi:phone"))` per consumer, and one `KusiModule` included in the app component.
- **AAPS 4 (Metro):** classes register themselves with `@ContributesIntoMap(AppScope::class)`, `@ContributesTo` and `@BindingContainer`. About zero lines in core.
- Manifest merging registers services, receivers and activities from the modules' own manifests.

### 3.3 The ledger (`kusi/KUSI_PATCHES.md`)

One row per core touch:

| id | file:symbol | kind (hook / limit / dosing / contract / build) | why | upstream status (in dev? issue #) | test that guards it | AAPS 4 action (drop / re-apply / rebuild) |
|---|---|---|---|---|---|---|

Rows marked dosing, limit or contract also carry "reviewed by / date". This file is the migration checklist.

### 3.4 Branch model

```
upstream/<aaps>+aisf<x>        read-only mirror of the AutoISF fork (later its 4.x branch)
  └ kusi/base-<ver>            = mirror tip + nothing (tag it)
      ├ kusi/t/<topic>         one branch per topic, one or a few clean commits each
      └ feature/kusi/<ver>     master = base + ordered patch stack (topic commits, no merge resolutions)
```

- Order of the stack:
  1. build/tooling
  2. kusi modules (additive)
  3. hooks
  4. backports (marked "drop on next base")
  5. dosing/limit patches, last and isolated
- New upstream release: create the new base, then `git rebase --onto` the stack. Use `git rerere` for repeated conflicts and `git range-diff old..new` to review each changed patch. No merge commits on master.
- Keep `feature/kusi/3.4.2.6` at aa16883b84 as a tag (`kusi-3.4.2.6-history`). Nothing is lost.

### 3.5 How each topic moves to 4

- **Drop list** (rows 1, 5, 11, 12, 15, 18, plus parts of 20 and 22): do not port. Before dropping, run the kusi test scenarios for that topic against dev's behaviour, or re-test the scenario by hand. Example: the loop-state tile, suspend and then resume from the watch.
- **Re-apply list** (rows 2–4, 6, 8–10, 14, 16, 17, 21, 23): one commit each on the new base, with its test. Rows 2–4, 8, 9, 16 and 23 need a loop-behaviour review before shipping.
- **Rebuild list** (rows 7, 13, 19, 20, 24–28): re-implement against dev's API inside the kusi modules.
  - Metro instead of Dagger.
  - Glance instead of RemoteViews.
  - dev's ConfirmAction lines and WizardDetail first; kusi only adds what is missing.
- **Upstream route.** Because AI-written PRs are not accepted, file **issues** with the finding and our test scenario:
  - SMB 6 s tolerance
  - token masking (security)
  - NSClient wake lock
  - fill-confirm without an id
  - UKF save rate
  - the resend preference filter

  The owner can write a PR himself if he wants. Every accepted fix is one less row in the ledger.

### 3.6 Tests that guard each change

- Every kusi module has its own unit tests. They already exist and can move with the code: WidgetLogicTest, the FaceLogic tests, WearConfirmDetailsTest, BolusRequestGuardTest and others.
- Every core hook or patch has a test next to it, named in the ledger. Examples: SmbIntervalTest, CommandSMBBolusTest, CompatDBHelperTest, LocalAlertUtilsImplTest.
- `DataHandlerMobileWatchBolusSafetyTest` (830 lines) becomes a **scenario list**: replay, stale, double tap, wear control off, old watch. On AAPS 4 it is re-run against dev's `bolusId` flow, whoever's code implements it.
- Add `make test` to run the kusi modules plus the modules named in the ledger. The 3 pre-existing `TriggerStepsCountTest` failures are a known baseline.
- **Restack check:** when the history is rewritten, `git diff aa16883b84 <new-tip>` must be empty. Same tree means the same APK behaviour.

### 3.7 Isolating the phone↔watch contract

- **On 3.4.2.6:** leave the existing kusi fields as they are. They have defaults, and the matched-pair install rule still holds. Add no new fields to `EventData`.
- **Future kusi messages:** add **one** generic core message, once:

  ```kotlin
  @Serializable data class KusiMessage(val type: String, val version: Int, val payload: String) : EventData()  // KUSI: wire-envelope
  ```

  The real kusi messages are a separate `@Serializable` sealed class in `kusi/core`, encoded into `payload`. Phone (`kusi/phone`) and watch (`kusi/wear-faces`) each register a handler. The core touch stays at one line forever, and the transport is not duplicated.
- **On AAPS 4:** add the same envelope at the **end** of `EventData`, because ProtoBuf numbering follows declaration order. Map `ConfirmDetails` warnings and effects onto dev's `ConfirmAction.lines` / `WizardDetail` where possible, and put only the rest in the envelope.
- Keep the matched-pair rule. Old watches must ignore unknown envelope types and must not crash.

### 3.8 What not to do any more

- Rewrite a stock class in place (Widget.kt, the confirm layouts), or delete stock resources.
- Comment out stock code (TreatmentActivity carbs page, tile confirm message). Use a kusi preference or a kusi tile source instead.
- Add fields in the middle of contract classes, or extend core interfaces for kusi-only data (DexcomTIR mean/HbA1c). Compute it in the kusi module.
- Merge work branches with hand-resolved conflicts into master. Rebase the topic and resolve once.
- Put signing, personal IPs or agent rules into upstream files.
- Bundle a backport, a battery fix and a dosing-adjacent change in one commit (as 9426dc3c1e, 53955413a9 and 51164f6930 did).

### 3.9 Migration plan for when AAPS 4 (+ AutoISF on 4) is ready

1. **Preconditions.**
   - 4.0 final is out, and the AutoISF base is decided (decision 1).
   - Check the Watch5 Pro's Wear OS version. Wear minSdk 30 is fine, but Watch Face Push needs Wear OS 6.
   - Settings export and DB backup are done. The 3.4→4 DB migration is one-way.
2. **Base.** Mirror the chosen 4.x+aisf branch to `kusi/base-4.x`. Build stock with our cert (Makefile plus injected signing). Run it on a **second device or an emulator**, not the loop phone.
3. **Drop check.** Go through the "drop" rows in the ledger. For each one, confirm dev covers it: read the code and run our scenario list. Turn any gap into an S re-apply row.
4. **Port the kusi modules.** Order: build, `kusi/core`, `kusi/phone`, `kusi/wear-faces`, `kusi/widget`, `kusi/lockscreen`. Each one Dagger→Metro, with its tests green.
5. **Hooks.** Re-add the ledger hooks one commit at a time.
6. **Dosing and limit patches last.** One commit each, compared line by line with the 3.4 version. Each gets a loop-behaviour review before it is included. Includes SMB 600 if kept, the div-by-zero guards if still missing in AutoISF-on-4, and SMB tolerance.
7. **Versioning.** versionCode ≥ the installed one (dev is also 1500, so check this). Add a kusi version-name suffix through a Gradle property. `make verify` must show the same cert, otherwise no in-place update is possible.
8. **Install.** Matched pair at a quiet moment (BG flowing, no bolus running). Watch loop runs and IOB closely in the first hours. Keep the 3.4.2.6 APKs and the exported settings.

### 3.10 First refactor step now, on 3.4.2.6, without touching dosing

The steps are ordered by risk. Each step must leave dosing code byte-identical.

1. **Docs only.** Write `kusi/KUSI_PATCHES.md` and `KUSI_BACKPORTS.md` from this inventory. Move the kusi rules to `kusi/CLAUDE.kusi.md`. Commit or deliberately drop the untracked `_docs/widget` and WHATS_NEW files. Optionally take c5df8a6d1a (version string only).
2. **Restack.** Build `feature/kusi/3.4.2.6-stack` from a14b8c7663 as about 15–20 topic commits. The rule: `git diff aa16883b84 <tip>` is empty. Same tree, so there is nothing new to review or install.
3. **Signing out of the build files.** The Makefile passes `-Pandroid.injected.signing.*`. Acceptance: `make verify` shows the same `6ff302f5…cd4b166b` cert for both APKs.
4. **Extract the watch faces into `:kusi:wear-faces`.** Add `KusiWatchFaceBase` and move the faces, resources and manifest entries. Core keeps only the enum, DI and config-mapping hooks. The face bolus request moves unchanged; it still only sends `ActionBolusPreCheck`. Re-test it on the watch anyway, because it is a treatment entry point.
5. **Later:** the loop watchdog and log definer into `:kusi:phone`, and the widget into `:kusi:widget` (decision 5).

## 4. The planned lock-screen widget, built additively

**Uncertain, check on the S24 first.** Stock Android phones (15/16) do not host third-party lock-screen widgets; Android 16's lock-screen widget hub targets tablets. One UI 7/8 lock-screen widgets appear to be limited to an allow-list of apps. A `keyguard` widget category may simply not show up. Realistic surfaces, in order:

1. **An ongoing notification as a Live Update, which also shows in the Samsung Now Bar.** This is visible on the lock screen and AOD. AAPS 4's persistent notification already does this, so on 4 we may only need styling or nothing at all.
2. A Samsung lock-screen widget, if One UI accepts ours.
3. AOD/clock integration. Probably not open to us.

The additive build is the same for every surface:

- **Module `:kusi:lockscreen`.** Its own notification channel (or its own provider), manifest and strings. It subscribes to existing events (new BG, calculation finished, loop result) and reads through existing interfaces: persistence, IOB/COB, profile, loop.
  - Core edits on 3.4.2.6: settings.gradle, the app dependency and the DI include, plus ledger rows.
  - On 4: Metro contributions and dev's `WidgetUpdater`/Glance, if it is a widget.
- **Share the logic.** Move the pure `WidgetLogic` (states, colours, stale/no-data, TIR rounding) into `kusi/core`, so the home widget, the lock-screen view and the watch show the same numbers.
- **Display only.** No bolus, no wizard and no loop actions from the lock screen. This keeps rule H13 from the widget spec: "Erst entsperren" (unlock first), no `showWhenLocked`. A tap opens AAPS, which still requires unlock and the AAPS protection.
- **ISF.** Display ISF uses the plain profile ISF, never `getIsfMgdl()` (rule H17: that call runs AutoISF and writes a loop-input cache). A unit test enforces this, as for the widget.
- **Privacy.** BG is visible to anyone who sees the locked phone. Add an option for "BG + trend only" or "hide when locked".
- **No duplication.** If we use a notification on 3.4.2.6, decide whether it *replaces* the stock persistent notification. Two ongoing BG notifications would be noisy. Replacing it means one hook (disable stock), not an edit.

## 5. Open decisions for the owner

1. **AutoISF on AAPS 4.** Options:
   - (a) Wait for a T-o-b-i-a-s `4.0.x+aisf3.2.x` branch. Recommended. It does not exist yet, and its existence is our inference.
   - (b) Use dev's built-in 3.0.1, which is a downgrade and gated to engineering mode.
   - (c) Port 3.2.1 ourselves. This is a dosing port and a big review. The unofficial RSC-RJCgit v4 port is a reference only, not a base.
2. **Keep or drop the SMB-minutes 600 cap and the AutoISF div-by-zero fallbacks?** Both are carried as isolated, reviewed patches if kept.
3. **Restack approval.** OK to create a restacked master next to the current one, with the old history tagged? No push until you say so.
4. **Upstream contributions.** Given "no AI-generated PRs": issues only, or will you write some PRs yourself (token masking, SMB tolerance, fill-confirm id)?
5. **Widget.** Keep replacing the stock widget, or ship the kusi widget as its own provider? Its own provider is additive, but you would re-add it on the home screen once.
6. **Lock-screen surface.** Notification/Now Bar or a real lock-screen widget (after checking on the S24), and how much BG data may show while locked.
7. **Which battery fixes to carry to 4** (NSClient, wear resend filter, UKF saves, xDrip throttle) after re-measuring on 4. Some may not be needed.
8. **AAPS 4 test device.** A second phone or emulator before the loop phone, and whether the Watch5 Pro gets Wear OS 6.
